# Sync Service — Decisions Log

Fill during the build: every non-trivial choice gets a row (Why +
Alternative Considered). Empty rows at review time read as undesigned.

| No | Decision | Why | Alternative Considered |
|----|----------|-----|------------------------|
| 1. | Project structure: src foldering, didnt follow the wp2 project structure | Considering The scope of this cli client project, consuming api, a little process, and data reporting. <br>Src layer was chosen in consideration of *Separation of Concern*. <br>**domain** defining dataclass in this case is Item. <br>**config** as central brain of project with a single source of truth, logger set here. <br>**service** as technical service, handling api calls, load & write file. <br>**use_cases** as core logic, business logic related, handle sync and report| a single well-structured main.py or simpler src foldering, combining the service and use cases. |
| 2. | cli routing: cli.argv_parser handle the argv request, return Request entity or direct shut down the system | new service/cli.py to handle the technical layer of cli parsing, written with full validation for each command, dataclass Request for routing in main.py | no service/cli.py for simpler foldering and calling function. |
| 3. | low level development: focus develop on technical first instead business layer. Storage as data manipulation module, every func params that is related to Item transfer got dataclass Item and return dataclass Item too. Write item_decoder not only as object hook for json loader, but also as decoder for csv and merge_data. service/api.py set with strict concern of fetching data from network, not handling the Item decode. create an Exception child with the name of its own representation| dataclass Item for consistencity data transfer object through the function. Item decoder written with the concern of reusable for the other function. service/api.py is a bridge for the network communication, so that the decode data isnt its concern. | not using the Item dataclass, it is easier to develop but cost us an inconsistent data. |
| 4. | wiring sync processor: call and implement the business flow of syncing data. set the forgotten asdict conversion before writing action. set for the positive case first, future repair when needed | finishing the flow faster | implementing the positive flow and all error cases at the same time, which makes it harder to isolate whether the core sync flow is working |
| 5. | wiring report feature: connect the report commands with the storage layer and adjust the error handling to follow the business requirements. Report reads the data from the written csv instead of using the sync result directly | report is required to use the persisted data as the source of truth. Connecting it after the sync flow also keeps the report implementation focused on reading and processing stored data | using the in-memory sync result for reporting, which would be simpler but would break the requirement that report reads the data from the file |
| 6. | Use timeout=30 for requests | the stub API is local and deterministic, but an explicit timeout is still needed so the network operation cannot hang indefinitely. 30 seconds gives enough tolerance for a slower development environment while keeping the request bounded | use a shorter timeout such as 5 seconds. It would fail faster, but could be less tolerant of a slow local environment |
