# Learning Rules (V2)

These rules are mandatory. Where an older document contradicts this
file, this file wins.

---

# Rule 1

Never copy code without understanding.

---

# Rule 2

Always think first.

Coding comes after reasoning.

---

# Rule 3

Read every error message.

Do not ignore stack traces.

---

# Rule 4

If stuck:

Debug. Search. Think.

Only then ask AI.

---

# Rule 5

The AI is not a code generator.

The AI is your instructor.

The AI does not solve your problems — it teaches you to solve them.

---

# Rule 6

Exercise volume is not fixed.

It depends on the topic's priority tier (see `ROADMAP.md`) and on
demonstrated mastery. When mastery and transfer are proven, stop drilling
and move forward.

---

# Rule 7

Every project must be completed independently.

The AI may clarify requirements and review code.

The AI never provides full implementations or step-by-step build plans
for weekly and stage projects.

---

# Rule 8

Readable code is more valuable than clever code.

Working code is not the finish line — good engineering code is.

---

# Rule 9

Premature optimization is discouraged.

Correctness first. Readability second. Performance later.

---

# Rule 10

Reflection is part of learning — and it is technical.

Not just "what did I learn", but: what did you decide, why, what
alternative did you consider, which bug took longest, what
misunderstanding caused it?

---

# Rule 11 — Hints

Hints are conceptual before they are concrete.

```text
Question → Conceptual hint → Diagnostic question → Specific hint → Pseudo-code → Solution
```

Never provide ready-to-use code, complete scripts, line-by-line fixes,
or pseudo-code that IS the solution.

A full solution is the final fallback — only after genuine attempt and
an explicit request.

For debugging: describe expected behavior vs observed behavior and ask
which operation causes it. The learner discovers the bug.

Hint usage is recorded as diagnostic information, never punishment.

---

# Rule 12 — Completion Requires Evidence

Submitting exercises does not complete a topic.

- CORE: understanding + independent implementation + at least one
  meaningful combination with previous concepts + demonstrated debugging
  + target mastery (Level 4).
- SUPPORTING: understanding + basic independent implementation +
  Level 3.
- AWARENESS: concept understood + can recognize and use a basic example.

Stage completion additionally requires the stage project, passed code
reviews, and demonstrated independent implementation.

---

# Rule 13 — Real-World First

Exercises use realistic scenarios whenever possible.

Every exercise is labeled `[REAL-WORLD]` or `[INTERVIEW]`.

Interview/DSA work lives in `DSA_TRACK.md`, not in stage lessons.

---

# Rule 14 — Cumulative Learning

New lessons must connect to previous knowledge where a meaningful
relationship exists.

Previous CORE concepts reappear in later exercises and projects
unannounced. Retrieval is implicit — no "this is a review" labels.

---

# Rule 15 — Quizzes

A quiz runs roughly every 3 related lessons.

Quiz results identify weak concepts → targeted practice follows.

---

# Rule 16 — Never Pre-Fill Solutions

`solution.py` (or any key file) starts blank.

The learner writes all code. Answers appear only after completion.

---

# Rule 17 — No Speed Optimization

The system optimizes for long-term competence, transfer, independence,
and engineering judgment — never for number of lessons completed.

But avoid over-learning: once a topic reaches its tier's target mastery
and demonstrates transfer, move forward.
